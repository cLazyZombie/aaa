# 이미지 원장 1024건 경계와 읽기 비용(t-1732)

## 변경과 비용

forget 전 작업 한도를 256건에서 1024건으로 올리고 검사·오류 문구는 `MAX_RETAINED_JOBS` 하나를 쓴다.
동시 생성 4건과 소유자별 미완료 4건은 유지한다. 목록 사유는 JSON 문자열 내용 기준 200바이트로 제한한다.
한글·제어 문자·따옴표·역슬래시의 직렬화 길이를 세며, 개별 status에는 원래 사유를 보존한다.
새 의존성·프로토콜 변경은 없다.

입력은 파일 5개 각각 50MiB가 아니라 **작업당 합계 50MiB**다.
결과는 최대 5개·각 50MiB이므로 작업당 입력·결과 파일 상한은 300MiB,
1024건은 `1024 × (50 + 5 × 50)MiB = 300GiB`(322,122,547,200바이트)다.
종전 256건의 75GiB보다 225GiB 늘어난다. DB·로그·실행 중 helper 임시 사본은 별도다.
forget 영수증은 계속 남으므로 300GiB를 host 전체 디스크 사용량의 상한으로 보지 않는다.

목록·새 요청 검사는 이미지 파일을 열지 않고 SQLite meta 원장을 읽어 역직렬화한다.
목록은 원장을 한 번, 새 요청은 보관 건수·소유자별 미완료 건수 계산을 위해 두 번 훑는다.
forget 영수증도 읽으므로 비용은 전체 영수증 수에 비례한다. 운영 원장·이미지 파일은 읽거나 지우지 않았다.

## 회귀 시험

`crates/aaa-host/src/image/tests.rs`에 다음 계약을 둔다.

- `ledger_accepts_1023_rejects_1024_and_forget_frees_a_slot`: 임시 Host·DB의 실제 image_request로
  1023건에서 새 ID 허용, 1024건에서 새 ID 거부와 파일·원장 미생성, 같은 ID 재조회,
  forget 뒤 자리 재사용과 영수증 보존을 확인한다. 작업마다 약 32KB 설명,
  참고 5개·합계 50MiB와 결과 5개·각 50MiB의 **메타데이터만** 넣는다.
  긴 한글·제어 문자·따옴표·역슬래시 사유, 64바이트 계정명과 최대 u64 토큰 수도 포함한다.
  목록 건수를 유지하고 실제 ImageReply와 FrameTx를 통과하는지 확인한다.
  이미지 파일·실계정 인증·생성 프로세스·고정 sleep은 쓰지 않는다.
- `list_reason_limits_json_bytes_without_cutting_unicode`: 전송 계약의 사유 요약을
  ASCII·한글·제어 문자·따옴표로 확인한다. UTF-8 문자를 자르지 않고 짧은 사유를 유지한다.

첫 시험은 요청 경계와 forget 슬롯 회귀를, 둘째는 다국어·JSON escape의 전송 한도 초과 회귀를 막는다.
웹 변경이 없고 실제 host 요청·agent frame owner에서 확인하므로 새 웹 E2E는 추가하지 않았다.

## 변경 전 실패와 변경 후 확인

실행은 모두 `aaa verify -- <명령>`을 거쳤다.

1. 종전 코드에서 경계 시험은 1023건의 새 요청을 「host 이미지 원장 한도(256건)에 도달했다」로 거부했다.
2. 한도를 바꾸기 전에 결과 5개·긴 한글 사유인 1023건의 실제 ImageReply가
   1,233,920바이트로 `TooLarge { max: 1048576 }`에 걸렸다(목록 읽기 66ms).
   문제를 보고한 뒤 목록 사유의 직렬화 길이 제한을 함께 수정했다.
3. 수정 후 관련 시험 2개가 통과했다(전체 2.06초).
   혼합 사유의 1023건 List는 66.6ms·886,782바이트, 1024건 List는 64.3ms·886,934바이트,
   1023건에서 새 Begin은 120.9ms였다. 시간은 개발 머신의 단일 표본이며 성능 합격선이 아니다.

이 규모의 메타데이터 조회와 수정한 응답 크기에서 추가 인덱스·페이지 나누기는 필요하지 않았다.
장기간 누적되는 forget 영수증과 이미지 외 디스크 사용량에는 별도 상한을 도입하지 않았다.

## 정규 검증 범위

[개발·착지 규칙](verification.md)에 따라 관련 owner인 aaa-host 전체 시험·strict Clippy와 공개 검사를 실행한다.
기준은 작업 시작 HEAD `cc4a6af5`이며 다음 진입점을 쓴다.

```sh
aaa verify -- nice -n 15 python3 scripts/verify.py develop --base cc4a6af5 --package aaa-host
aaa verify -- nice -n 15 cargo fmt --all --check
```

개발 검증 결과는 `target/verification/develop-*/result.json`에 보존한다.
최종 통합 SHA의 전체 gate·양 OS cross와 배포 검증은 착지 승인 뒤 별도 단계다.
