# 정상 조회 응답의 5시간 필드 진단(t-1454)

## 범위

조회 인증 저장 성공과 5시간 창의 새 관측은 별개다. 정상 사용량 조회에서 주간만 저장된 경우,
기존 기록만으로는 5시간 필드가 빠졌는지·null인지·숫자 형식이 달랐는지 구별할 수 없다.

정상 JSON 객체 응답에만 「Claude 5시간 응답 진단」을 기록한다.

| 필드 | 의미 |
| --- | --- |
| five_hour_type | five_hour의 존재·JSON 유형 |
| utilization_type | 그 안의 utilization 유형 |
| resets_at_type | 그 안의 resets_at 유형 |

유형은 missing/null/boolean/number/string/array/object의 정적 문자열뿐이다.
인증·메일·계정명·응답 값·원문·임의 키 목록·오류 본문은 새 진단에 포함하지 않는다.
기존 파싱·수치·캐시·갱신·429 backoff·실행 인증·API·프로토콜은 바꾸지 않는다.

## 개발 검증

자기 worktree·target과 기존 kache, `aaa verify`·nice 15로 확인했다.

| 검사 | 결과 |
| --- | --- |
| host usage owner | 19개 통과 |
| host all-targets strict Clippy | 통과 |
| fmt·공개 검사·diff check | 통과 |

- 유형 keeper는 absent/null과 JSON 유형을 구별하고 임의 공급자 문자열 및 그 8바이트 조각이 안전 요약에 섞이지 않음을 확인한다.
- 가짜 HTTP 서버의 정상 주간 응답과 없는/null/내부 utilization=null인 5시간 응답에서 주간 수치를 유지하며 5시간 0%를 합성하지 않음을 검사한다.
- 기존 owner는 실제 0% 관측, 401/403/429/5xx 구별, 인증 회전·버전 보존과 backoff를 계속 검사한다.
- 첫 개발 컴파일은 성공 응답이 Map인 것을 Value로 받으려 해 실패했다. 원문을 보존하고 Map을 직접 받도록 고쳐 검증했다. 판정·시한을 완화하지 않았다.

## 운영 확인의 한계

조사 당시 대상의 host 상태는 조회 HTTP 429와 재조회 대기였다. 추가 진단 GET은 보내지 않았고
키·인증값도 실제 금고에서 읽지 않았다. 제공자가 정상 응답을 다시 줄 때의 필드 유형을 아직 관측하지 못했다.
따라서 5시간 누락 원인이나 복구를 확정하지 않는다. 429는 사용량 조회 제한이며 모델 한도나 로그인 실패로 해석하지 않는다.

이 후보의 착지·배포는 별도 승인이다. 배포 뒤 다음 정상 조회에서 고정 유형만 읽어 원인을 좁힌다.
실제 재로그인·인증 교체·강제 재조회는 요구하지 않는다.
