# Claude 조회 인증 분리(t-1454)

실행용 setup-token과 사용량 조회 인증을 분리한다. 실제 로그인·운영 인증·프로세스·설치·배포는 변경하지 않았다.
개발 확인 범위는 `docs/verification.md`의 관련 owner다. 최종 통합 gate·OS cross·production은 착지 승인 뒤 별도다.

## 계약

- 공식 CLI를 격리해 새 조회 로그인만 받으며, 등록 메일(모르면 사람이 지정한 기대 메일)과 일치해야 저장한다. 다른/불명 신원·취소·기기 해제·로그인 중 실행 재등록을 거부한다.
- 별도 봉투 암호화 금고, 조회 인증 단독 갱신과 회전값 선저장, 판 비교로 늦은 저장 거부. 실행 토큰·세대·계정 인증 날짜를 유지한다.
- 같은 조회 인증의 400/401/403 재요청은 멈추고 새 조회 로그인으로 해제한다. 429 대기는 새 조회 로그인에도 유지한다. 모델 배정 한도로 올리지 않는다.
- agent의 창 입력 누락, host의 조회 상태, 마지막 수치·시각을 따로 전달한다. 모르는 창의 숫자를 합성하지 않는다.

## 확인 기록

모든 확인은 `aaa verify -- nice -n 15 ...`로 실행했다. 이 후보의 관련 개발 확인이며 착지 최종 gate가 아니다.

| 범위 | 결과 | 확인한 경계 |
| --- | --- | --- |
| `aaa-proto` | 50개 통과 | Rust 계약·TS 생성과 호환 |
| `aaa-host --lib usage::tests::` | 17개 통과 | 독립 인증·갱신 회전·403 중단·429 보존·늦은 응답·기존 소비자 |

| `aaa-host --lib quota::tests::` | 6개 통과 | 창 누락과 조회 거부 분리·이력·별칭 변경 |

관련 Rust owner(`aaa-host`·`aaa-agent`·`aaa-proto`·`aaa`)의 all-targets strict Clippy와 `cargo fmt --all`도 통과했다.
`check-public.sh`도 통과했고 `docs/testing.md`에는 링크 한 줄만 추가했다(1,018,750바이트로 1MiB 아래).

후보 작성 중 확인은 미커밋 상태이므로 자동 검증 원장에는 수집되지 않았다. 실행 로그는 비공개 `target/t1454-usage-auth/`에 보존했다.
공개 문서·시험 자료에는 지어낸 별칭·메일과 loopback만 썼다. 원시 인증·hook 입력·오류 본문은 공개 산출물에 넣지 않았다.

## 개발 중 발견과 수리

- 첫 컴파일은 import가 모듈 문서 주석을 앞서고 초기값 추가가 enum 선언까지 적용돼 실패했다. 원문을 보존하고 대상 편집을 수리했다. 착지 gate는 실행하지 않았다.
- 후속 컴파일에서 같은 잘못된 삽입의 match 분기와 추가 필드의 shorthand 초기화 누락을 확인해 모두 수리했다.
- 시험 편집의 단언 삽입 위치와 canary 도우미 반환 타입을 바로잡았다.
- 기존 sidebar 시험은 실행 인증으로 403을 받도록 구성돼 있었다. 독립 조회 인증을 명시적으로 연결하도록 fixture를 바꾸고 기존 403·관측 초기화·Authorization 단언을 유지했다. 실행 인증만 있을 때 요청 0건과 조회 인증 필요 상태도 추가했다.
- strict Clippy가 지적한 중첩 조건을 합쳤다. 시한 연장·기대값 완화·재실행으로 실패를 덮지 않았다.

## 제공자 경계와 한계

[공식 인증 문서](https://code.claude.com/docs/en/authentication#generate-a-long-lived-token)는 setup-token의 용도를 모델 요청으로 한정한다.
[공식 CLI 문서](https://code.claude.com/docs/en/cli-reference)의 구독 로그인과 격리 설정 폴더를 따른다.
조회 인증 파일/Keychain 모양과 refresh endpoint는 기존 usage 수집기 및 검토한 공식 CLI 구현과 맞췄다.
제공자가 사용량 endpoint·인증 저장 모양을 바꾸거나 새 조회 인증에도 권한을 거부하면 숫자 복구는 보장하지 않는다.
실제 브라우저 로그인과 다음 실제 hook·조회 성공은 별도 승인 뒤 확인해야 한다.

등록 메일이 없는 실제 대상도 기대 메일 입력으로 사용할 수 있게 했다. 실행용 토큰만으로 계정 신원을 증명할 수는 없으므로 사람이 별칭과 기대 메일의 결속을 확인해야 한다. 입력은 Debug에서 가려지고 실행 인증 메타데이터는 유지한다.
