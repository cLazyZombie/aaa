# 다시 연 앱의 첫 화면 왕복 줄이기(t-2150)

휴대폰에서 앱을 완전히 닫았다 다시 열면 첫 화면이 쓸 수 있게 되기까지 서버 왕복이 차례로 이어졌다.
host의 시작 조회(기기 확인·열린 thread·대화 읽기·pane 목록)는 각각 수십 ms라 서버 처리는 원인이 아니었다.
실험실에서 망 지연을 늘리면 첫 대화·입력 가능 시각이 왕복 시간에 거의 비례해 늘었다(RTT 100·200·300ms에서 입력 가능 1.3~1.9초·2.2~3.3초·3.0~4.6초).

| 차례 | 고치기 전 | 고친 뒤 |
| --- | --- | --- |
| 기기 확인(`GET /api/v1/me`) | 응답을 받은 뒤 본 화면을 띄우고 상태 연결을 열었다 | 마지막으로 확인한 기기면 응답 전에 본 화면을 띄워 상태 연결과 함께 보낸다 |
| 기억한 coordinator pane | 열린 thread 목록 응답까지 기다렸다 | pane 목록(상태 연결의 첫 사건)에 돌고 있으면 바로 연다 |
| 첫 화면 셸(`/`) | service worker가 네트워크 먼저로 받았다(새 연결·셸 왕복 뒤 앱 시작) | 캐시한 앱 셸로 바로 열고 host의 셸은 뒤에서 받아 다음 실행에 쓴다(사용자 q-4688 1A) |

확인 응답이 기억과 같으면 화면을 다시 만들지 않는다. 401이면 기억을 지우고 연결 화면으로, 닿지 못하면 「host에 연결할 수 없다」로 바꾼다.
배포 뒤 첫 실행은 옛 빌드라 「앱 다시 열기」 줄이 뜬다. 그 단추는 `?fresh` 표지를 붙여 열어 worker가 네트워크 먼저로 host의 셸을 준다.
다른 화면 이동은 네트워크 먼저이고, 셸 사본은 첫 화면 주소의 HTML만 둔다.
안전 모드 host는 앱 API에 `unavailable`로 답한다. 캐시한 셸로 뜬 앱은 그때 표지를 붙여 한 번 다시 열어 안전 모드 화면에 닿는다.

## 실험실

- 격리한 실제 host·agent, coordinator pane과 Claude 대화 기록, 끝난 thread 2,150개(운영과 비슷한 규모)를 쓴다.
- WebKit, iPhone 화면(390×844, 터치)으로 대화 보기를 연다.
- 브라우저와 host 사이에 지연 proxy를 둔다. 한 방향 50ms(RTT 100ms)이고, 새 연결의 첫 요청은 TCP·TLS 준비를 흉내 내 RTT 2번 더 늦춘다.
  proxy는 평문 HTTP/1.1이라 동시 연결 6개 한도의 줄 서기가 생긴다. 실제 HTTPS(HTTP/2)보다 그 부분은 길게 잰다.
- 「다시 연 앱」은 service worker와 캐시가 있는 같은 브라우저 context에서 살아 있는 연결을 모두 끊고 새 페이지를 연다.
  세 번 중 첫 번은 캐시를 채우는 판이라 뺐다.
- 시각은 페이지 시작부터다. 첫 대화는 대화 줄이 DOM에 생긴 때, 입력 가능은 대화 입력창의 그림 첨부 단추가 켜진 때다.

| 다시 연 앱(RTT 100ms) | 고치기 전 | 고친 뒤 |
| --- | ---: | ---: |
| 상태 연결 open | 906·926ms | 802·802ms |
| 첫 대화 | 1,538·1,582ms | 1,274·1,277ms |
| 입력 가능 | 1,447·1,547ms | 1,286·1,289ms |

셸 캐시 우선까지 넣은 최종 판(같은 조건)은 상태 연결 open 451·454ms, 첫 대화 1,028·1,054ms, 입력 가능 872·875ms였다. 표의 「고친 뒤」는 셸 캐시 우선 전 판이다.

캐시가 없는 첫 방문도 첫 대화 1,811~1,892ms → 1,562~1,615ms였다. 각 수치는 한 실행의 표본이다.

## 시험

- 웹 E2E 143(WebKit 휴대폰): 짝지은 뒤 새 페이지를 주소 없이 연다. 기기 확인 응답과 열린 thread 목록 응답을 route로 붙잡은 채
  상태 WebSocket 요청과 기억한 coordinator의 대화 줄을 기다린다. 놓은 뒤에도 상태 연결이 하나인지, 취소한 기기는 기억이 있어도
  연결 화면이 되고 기억을 지우는지 본다. 기기 확인을 기다리게 되돌리면 상태 연결 단계에서, thread 목록을 기다리게 되돌리면
  대화 줄 단계에서 실패하는 것을 확인했다.
- 웹 E2E 143 셸 단계(WebKit, 실제 service worker): 캐시한 셸에 표지를 심고 다시 열어 표지가 있는 화면으로 열리는지, 그 뒤 host의
  셸이 캐시 자리를 바꾸는지 본다. 상태 사건의 웹 빌드를 다르게 바꿔 「앱 다시 열기」 줄을 띄우고, 캐시를 다시 옛 셸로 둔 채 단추를
  누르면 표지 없는 host 셸이 열리고 주소의 `fresh`가 지워지며 자리 hash가 남는지 본다. 네트워크 먼저인 옛 worker는 「캐시한 셸로
  열려야 한다」에서, 단추를 `reload()`로 되돌리면 「앱 다시 열기는 host의 셸이어야 한다」에서 실패하는 것을 확인했다.
  이어서 host.toml을 깨뜨려 실제 안전 모드 host로 다시 띄우고, 같은 브라우저로 첫 화면을 열면 표지가 붙은 주소의 「aaa 안전 모드」
  화면에 닿는지 본다. `unavailable` 때 다시 열지 않게 되돌리면 안전 모드 화면 기다림에서 실패한다.
- `web/test/sw-navigate.test.mjs`: 내보내는 sw.js를 가짜 caches·fetch로 돌린다. 캐시한 셸은 네트워크 답 전에 답하고 받은 셸과 그 파일을
  뒤에서 둔다. `?fresh`·파일 보기·셸이 아닌 캐시는 네트워크 답이고 파일 보기 답은 셸 자리에 두지 않는다. 끊기면 캐시 셸·offline.html.
  옛 worker에서는 앞 두 시험이 실패한다.
- `web/test/freshShell.test.mjs`: 표지 붙이기·지우기와 sw.js의 표지 이름이 같은지.
- `web/test/signedIn.test.mjs`: 확인한 역할·ID만 저장, 401에서 지움, 모르는 역할·깨진 값·막힌 저장소는 기억 없음.
