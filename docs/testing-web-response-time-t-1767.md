# 첫 접속·질문 답 응답 시간(t-1767)

웹에서 처음 접속해 목록이 뜰 때까지와, 「답할 것」 카드에 답한 뒤 화면이 바뀔 때까지를 먼저 재고 느린 곳만 고쳤다.
캐시 층·새 프로세스·새 의존성은 더하지 않았다. FRONT_API와 응답 꼴은 그대로다.

## 잰 방법

- 운영 host(읽기 전용): 정적 자산은 curl로, 접속 뒤 읽는 조회 요청은 같은 머신 front socket에 웹과 같은 요청을 보내 처리 시간과
  응답 크기를, 답 전달은 흐름 사건의 `message_queued`→`message_accepted` 간격으로 쟀다. 웹 기기를 새로 짝짓지 않았다.
- 실험실 브라우저: `web/e2e/tools/perf-measure.mjs`. 실제 host·agent에 thread 1,755개와 답한 것 1,004건을 넣고 Chromium·WebKit
  (390×844)으로 연다. 탐색 시작부터의 화면 단계, API 요청별 시간·푼 크기·전송 크기, 「답 보내기」 누름부터 카드 변화까지를 남긴다.
  망 흉내는 Chromium DevTools다(LTE: 10 Mbps·60 ms, 느린 망: 1.6 Mbps·150 ms. WebSocket에는 걸리지 않는다). 한 조건 5회(느린 망은 3회)의 중앙값이다.

```sh
cargo build --profile e2e -p aaa && (cd web && npm run build) && cargo build --profile e2e -p aaa
NODE_PATH=<playwright 1.64.1> AAA_PERF_OUT=<결과.json> node web/e2e/lib/child.mjs web/e2e/tools/perf-measure.mjs
```

시험이 아니라 측정 도구다: 단언이 없고 gate에 들지 않는다. 고치기 전 실행 파일은 `AAA_BIN`으로 준다.
실험실 자료에는 할 일 queue와 보고서 목록을 넣지 않아 API 합계(1.4 MB)가 운영(3.4 MB)보다 작고, 지어낸 글이라 운영 자료보다 잘 줄어든다.

## 찾은 원인

| 곳 | 고치기 전 | 근거 |
| --- | --- | --- |
| thread 질문 카드 답 | 누르면 질문 카드는 약 0.04초에 사라지고 「답한 것」 카드는 약 0.9초 뒤에 떴다. 그 사이 「질문을 찾을 수 없다」 안내가 보였다 | host가 답을 기록한 thread 사건은 바로 오지만, 카드는 thread 전달(운영 중앙값 635 ms, 90% 842 ms, 붙여넣기 뒤 고정 300 ms 포함)과 그 뒤의 「답할 것」 다시 읽기(운영 415 KB, 처리 150~350 ms)를 차례로 기다렸다 |
| 접속 뒤 읽는 API | 압축 없이 나갔다. 운영 합계 약 3.4 MB(thread 전체 2,057 KB, 할 일 511 KB, 답할 것 415 KB, 보고서 375 KB) | 정적 자산과 보고서 보기는 gzip 협상을 하지만 `/api/v1/call` JSON에는 없었다 |
| 확인 필요 post 답·답함 표시·지우기·자동 모드 | 쪽 없는 「답할 것」 전체를 돌려줬다(운영 2,330 KB). 웹은 그 본문을 쓰지 않고 다시 읽는다 | front socket에서는 frame 상한(1 MiB)을 넘어 CLI가 처리 뒤에 `too_large`를 받았다 |
| thread 전체 목록 | 100개씩 18쪽을 차례로 읽었다 | 쪽마다 왕복 한 번이다. host 상한은 200개다 |

## 고친 것

- 웹: 보던 질문 카드의 thread에 host가 답을 기록하면(thread 사건) 그 질문과 답으로 「답한 것」 카드를 바로 그린다(`asksModel.answeredNow`).
  host 기록을 다시 읽으면 같은 카드가 그 기록으로 이어진다. 그동안 「지우기」와 물은 때는 없고, 답에 붙인 그림은 프로젝트 uploads에서 읽는다.
  같은 보고의 답이고 보던 카드에서 이어질 때만이다(기록을 지운 옛 답을 되살리지 않는다).
- host: 1 KiB 이상의 `/api/v1/call` 답을 브라우저가 받는다고 한 gzip으로 보낸다. 정적 자산과 같은 협상기를 쓰고 압축 수준은 보고서 보기와 같다.
- host: 조작 뒤의 답은 쪽 있는 「답할 것」(원문 첫 쪽과 색인)이다. 웹의 조작 응답은 그 조작의 사건이 시작한 읽기를 버리지 않는다(`AsksReload.follow`).
- 웹: thread 목록은 200개씩 청한다. 할 일 확인 필요 답 뒤에도 쪽 있는 목록으로 다시 읽는다.

서버가 전달을 기다리지 않고 답하게 바꾸는 안은 접었다. 화면은 이미 host의 기록 사건으로 바뀌고, 기존 시험(E53)과 CLI가
「응답 = 전달 끝」에 기대고 있다. 붙여넣기 뒤 300 ms 간격도 줄이지 않는다(Enter가 붙여넣기 줄바꿈으로 먹히는 것을 막는다).

## 전후(실험실, ms)

「답 보내기」 누름부터:

| 단계 | Chromium | WebKit |
| --- | ---: | ---: |
| 「답한 것」 카드 표시 | 892 → 45 | 929 → 64 |
| 「찾을 수 없다」 안내가 보인 시간 | 724 → 0 | 871 → 0 |
| thread가 답을 받음(바뀌지 않음) | 471 → 493 | 483 → 495 |

확인 필요 post 카드(Chromium): 응답 본문 4,427 KB(압축 없음) → 384 KB(gzip), 「답한 것」 카드 431 → 429.
응답만 줄였을 때는 응답이 다시 읽기보다 먼저 와 그 읽기를 버리고 한 번 더 읽어 615까지 늦어졌다. `follow`가 그것을 막는다.

첫 접속(Chromium, 탐색 시작부터). 화면 틀과 열린 작업 표시는 그대로이고 그 뒤의 읽기가 줄었다:

| 조건 | 「답할 것」 목록 | 모든 읽기 끝 | API 전송 | API 요청 수 |
| --- | ---: | ---: | ---: | ---: |
| LTE, 캐시 있음 | 1,168 → 685 | 2,874 → 1,322 | 1,403 → 65 KB | 42 → 33 |
| LTE, 캐시 없음 | 1,760 → 1,240 | 3,427 → 1,852 | 같음 | 같음 |
| 느린 망, 캐시 있음 | 4,820 → 1,368 | 10,667 → 2,812 | 같음 | 같음 |
| 느린 망, 캐시 없음 | 7,966 → 4,503 | 13,805 → 6,008 | 같음 | 같음 |
| loopback, 캐시 있음 | 657 → 652 | 829 → 735 | 같음 | 같음 |

바뀌지 않은 것: 화면 틀(LTE 캐시 있음 0.28초)과 열린 작업·질문 카드 표시(0.49초). 캐시가 없을 때는 JS 묶음 544 KB(gzip)를 받는
시간이 그대로다(LTE 0.83초, 느린 망 3.6초). 운영 자료의 gzip 비율은 약 5배다(3.4 MB → 0.71 MB, zlib 기본 수준으로 잰 값).

고친 뒤 값은 최종 커밋의 e2e 실행 파일로 잰 것이다. 고치기 전 값은 기준 커밋의 실행 파일(`AAA_BIN`)로 쟀다.

## 필요한 owner

| 시험 | 지키는 동작 |
| --- | --- |
| 웹 E2E 53 「답하면 … 답한 카드가 바로 뜨고 host 기록으로 이어진다」 | 다시 읽기를 붙잡은 동안 답한 카드 표시, 안내 미표시, 지우기는 host 기록 뒤, 같은 카드 유지 |
| 웹 유닛 `asksModel` 「방금 답한 thread…」 | 답한 것 모양과 카드 key |
| 웹 유닛 `asksReload` 「조작 응답은…」 | 읽던 목록 적용 뒤 한 번 더 읽기, 읽는 것이 없으면 바로 읽기 |
| 웹 유닛 `threadReload` | 200개 요청 |
| host `large_api_answers_are_gzipped_only_when_accepted` | 문턱·협상·거절(`q=0`)·원문 일치·`no-store`·UTF-8 표지 |
| host `operation_answers_stay_paged_with_large_history` | 쪽 없는 전체가 1 MiB를 넘어도 조작 답은 512 KiB 안, 색인 전부·원문 첫 쪽 |
| 기존 E2E 53·69·100·113·123·128·129 | 답·확인 카드·자동 모드·일괄 지우기·초안·할 일 확인·첫 화면 |

E2E 53 「t-0621 원문」 단계는 답한 카드가 뜬 뒤 바로 Follow-ups·inbox를 읽었다. 카드가 API 응답(전달 끝)보다 먼저 뜨게 되어
「질문별 원문이 Follow-ups에 없다」로 실패했고, 같은 파일의 「여러 줄」 단계(t-1638)처럼 `thread_answer` 응답을 관측한 뒤 읽게 고쳤다.
기대값·시한은 그대로다.

개발 검증(최종 커밋): host 893개 통과·strict Clippy, 웹 타입·번들·유닛 720개, 웹 E2E 전체 40개 파일 312단계 통과, 공개 검사 통과.
새 E2E 단계는 기준 커밋의 실행 파일에서 답한 카드를 기다리다 30초 시한으로 실패한다.

## 남은 것

- 운영 host에서는 고친 판을 배포한 뒤에야 다시 잴 수 있다. 위 전후는 실험실 값이다.
- 답이 전달 전에 거절되면(확인창·입력창 글 등) host가 답 자리를 풀어 질문 카드가 돌아온다. 두 thread 사건 사이에 화면이 그려지면
  전에는 「찾을 수 없다」가, 지금은 답한 카드가 잠깐 보인다. 같은 머신 실험실에서는 두 사건이 한 번에 그려져 재현되지 않았다.
- 캐시 없는 첫 접속의 JS 묶음 크기, 접속할 때 두 번씩 읽는 조회(할 일·보고서 목록 등), 「답할 것」 색인을 만드는 host 시간은 손대지 않았다.
