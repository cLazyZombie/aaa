# 새 보고·대화 출력 중 입력 지연 수리(t-1873)

## 이전 수리와 이번 원인

- t-0859(ba47f748)는 인앱 팝업 SVG 필터를 카드 폭으로 제한했다. 현재도 유지된다.
- t-1352(24c7579c)는 파일·링크 열기 함수 참조가 부모 렌더마다 바뀌지 않게 했다. 현재도 유지된다.
- t-0536(b520791a)은 늦은 커서 복원이 새 선택을 덮는 경합을 수리했다. 이번 지연과는 다른 경로다.

새 보고·질문 정보가 생길 때 `AppRefContext` 값은 실제로 바뀐다. 모든 Markdown `Inline`이 그 Context를 읽어,
참조가 없는 문단·외부 링크·파일 경로까지 다시 처리했다. 보관 중인 숨은 대화도 대상이었다.
`Markdown`의 memo만으로는 하위 Context 소비자 갱신을 막지 못한다. t-1352와 같은 Context 전파 계열이지만,
파일 열기 함수 참조 수리의 재발은 아니다.

출력 갱신 때 기존 `AgentTurn`도 다시 실행되며 복사용 일반 텍스트를 만들었다. 별도 CPU 프로파일에서
이 재계산을 확인했다. 새 답 추가만으로는 기존 링크 재처리가 생기지 않았다.

## 변경

`Markdown.tsx`는 참조 후보가 있는 줄만 `AppInline`에서 Context를 구독한다. 나머지 줄은 일반 표시를 유지한다.
아직 등록되지 않은 짧은 ID도 후보에 남겨, 작업이 생기면 실제 링크로 바뀌게 한다. 중첩 강조·링크의 자식도
각자의 표시 경계를 따르며, 질문 칩은 바뀐 질문·선택지를 계속 받는다.

`Chat.tsx`의 `AgentTurn`은 본문과 활성 상태가 같으면 재사용한다. 복사 상태의 자체 갱신과 활성 상태 변경은
계속 반영된다. 팝업 CSS·알림 정책·backend·protocol·의존성 변경은 없다.

## 입력 지연 비교

실제 격리 host·agent·PTY와 앱, 일반 production 웹 번들로 비교했다. backend는 e2e 빌드이며,
Chromium의 CPU를 CDP로 4배 느리게 했다. 숨긴 대화의 답 120개와 현재 대화의 답 40개를 실제 앞 기록 API로
모두 읽었다. 답 하나에는 링크·파일 경로·강조가 있는 20개 문단을 넣었다.

출력 없음, 새 답 추가, 다른 작업의 새 보고·질문 도착에서 실제 키를 연속 입력했다. 새 보고는 명시적 ticker tick으로
수집했고, 팝업 표시와 실제 펼침 애니메이션 완료까지 입력했다. 고정 sleep으로 끝내지 않았다.

| 조건 | 원본 최대 입력 왕복 | 수정 최대 입력 왕복 | 원본/수정 중앙값 |
| --- | ---: | ---: | ---: |
| 출력 없음 | 25.6ms | 25.1ms | 18.5 / 18.8ms |
| 새 답 출력 | 60.9ms | 47.3ms | 18.6 / 19.0ms |
| 보고·팝업 표시 전체 | 230.4ms | 48.5ms | 19.1 / 19.8ms |

| 보고·팝업 구간 | 원본 | 수정 |
| --- | ---: | ---: |
| 바뀌지 않은 본문의 링크 재처리 | 6,400회 | 0회 |
| 가장 긴 프레임 간격 | 216.6ms | 33.4ms |
| 50ms 이상 브라우저 작업 | 3회 | 0회 |
| 가장 긴 브라우저 작업 | 228ms | 관측 없음 |

각 조건을 한 번씩 비교한 진단값이다. 입력 횟수는 원본 25/105/173회, 수정 25/128/171회다.
입력 왕복에는 자동화 통신 비용이 포함되며, 사용자 기기의 지연 보장이나 E2E 합격선으로 쓰지 않는다.
모든 조건에서 입력 글·커서·포커스가 유지됐다. 수정판에서 글 가운데 한글을 넣은 `앞가나뒤`와 실제 파일 열기도 확인했다.

초기 진단의 본문 전체 locator 검색은 측정 비용을 섞었다. CPU 프로파일로 확인한 뒤 최종 비교에서는 마지막 줄의
DOM 변화만 관측했다. 프로파일용 HTML 가로채기가 Chromium의 local network access 검사를 일으킨 문제도
실제 host HTML과 자산 교체를 분리해 확인했다. 위 표는 자산 가로채기·CPU profiler가 없는 일반 내장 번들의 최종 값이다.

## 회귀 시험

기존 E2E117의 inbox 입력·IME·파일 열기 네 조합은 유지하고, 새 보고·질문·답 단계 네 개를 더했다.
실제 앱에서 coordinator 대화를 숨겨 보관하고 다른 pane의 글 가운데를 작성한다.

1. 아직 없는 작업 ID가 들어 있는 평문·강조·code와 명시적 질문 참조를 표시한다.
2. 실제 thread를 만들면 평문·강조·code의 ID 세 개가 링크로 바뀌어야 한다.
3. 실제 보고를 쓰고 ticker가 수집하면 질문 칩 두 개와 인앱 팝업이 나타나야 한다.
4. 보고의 질문을 바꾸면 기존 칩도 새 질문·선택지를 받아야 한다.
5. 새 답을 실제 대화 기록에 붙이고 DOM 반영을 기다린다. 바뀌지 않은 본문의 링크 재처리는 0회여야 한다.
6. IME 조합 중 초안·가운데 커서·포커스·편집 가능 상태와 다음 글 입력이 유지돼야 한다.

본문 탐침이 처음 표시할 때 실행됐음을 먼저 확인한다. 새 답의 링크는 기존 본문과 다른 주소를 써,
새 본문의 정당한 처리를 기존 본문 재처리로 세지 않는다. 시한이나 입력 지연 임계값을 완화하지 않았다.

원본 실행 파일은 새 Chromium 데스크톱 단계에서 `168 !== 0`으로 실패했다. 새 ID·질문 갱신과 새 답은
이미 반영됐지만, 기존 본문 링크가 168번 다시 처리됐다. 수정판의 새 네 조합은 모두 통과했고,
각 단계는 같은 머신의 관련 검증 묶음에서 약 2.4~2.9초였다.

  --spec 09,23,69,103,117,122 --logs target/verification/t-1873-develop

- E2E117의 기존 네 조합과 새 네 조합: 모두 통과.
- 공개 검사: 개발 묶음에서 통과.
- 변경 범위는 웹 소스·spec·Markdown 문서다. 관련 검증 묶음은 74초였다.
