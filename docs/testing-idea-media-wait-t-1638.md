# E2E130 그림 전달 대기 조사·수리(t-1638)

## 원 CI 증거와 한계

실패 SHA는 `039caefd9ecab8128d6985c594ea6cbefbe0a467`이며
[원 CI job](https://github.com/cLazyZombie/aaa/actions/runs/42430342274/job/128577626554)의 첫 실행이다.
웹 E2E의 50개 작업 중 E130 하나가 실패했다. 업로드·CLI 붙이기·그림 편집·휴대폰 조작·넘기기 창의
저장소 기본값 검증은 통과했다. 마지막 그림 전달 단계는 기존 120,000ms 상한에 걸렸다.

원본 job 로그와 [원 산출물](https://github.com/cLazyZombie/aaa/actions/runs/42430342274/artifacts/13597438319)을 읽었다.
산출물에는 E130의 화면·요청 경계·실험실 DB·thread 파일이 없고, 다른 시험의 진단과 실행 시간만 있다.
실패 실험실의 host·agent 로그에는 준비 단계의 셸 입력 한 건만 있고 thread 시작 입력은 없다.
따라서 thread 시작 이전에 멈췄다는 범위까지만 확인된다. 넘기기 API 응답·할 일 화면 이동·그림 해독 중
정확히 어느 await였는지는 원 CI 자료로 확정할 수 없다.

기준 SHA의 Rust·제품 코드를 유지하고 마지막 단계 위치 계측을 넣은 로컬 첫 실행과
새 실험실 반복 20회·30회는 모두 통과했다. 첫 반복은 위치 로그·그림 상태 조회를 넣었고,
두 번째는 정상 경로의 추가 Playwright 왕복 없이 위치 변수와 해독 상태만 기록했다.
이 51회 통과를 원 CI 수리나 회복의 증거로 세지 않는다.

## 실행 경로와 분류

- 제품은 `ideas.rs::idea_handoff`에서 그림을 uploads에 복사하고 task 메모에 링크를 쓴다.
  웹은 `TaskAttachments.tsx`의 lazy 썸네일로 그린다. thread 시작 때 첨부·노트와 링크가 작업 폴더로 간다.
- 기존 시험은 첨부 DOM 개수만 확인한 뒤 화면 안으로 스크롤하지 않고 `img.decode()`를 기다린다.
  화면 밖 lazy 그림은 이 호출만으로 다운로드가 시작되지 않을 수 있다.
- 원 CI의 자원 부하는 기록됐지만 고갈·연결 실패나 요청 정지를 증명하는 자료는 없다.
  제품·fixture·자원 중 원 CI의 분류는 미확정이다.
- t-1627의 변경은 coordinator PostToolUse hook과 nudge다. E130의 custom 셸은 hook을 호출하지 않고
  coordinator도 열지 않는다. nudge의 시간 대기는 coordinator가 있는 분기에서만 설정한다.
  공통 ticker에는 변경이 있지만 이 실행 경로와 원 실패를 연결하는 증거는 없다. 커밋 순서로 인과를 단정하지 않는다.

## 별도로 재현한 시험 대기 결함

넘기는 정리 메모를 길게 하여 실제 할 일 상세의 lazy 첨부가 화면 밖에 있도록 했다.
같은 실제 host·agent·그림·DOM을 쓰며 제품 코드는 바꾸지 않았다.

기존 대기는 첫 그림 해독에서 120초 상한으로 실패했다. 그림은 DOM에 연결된 채 y=5263.625에 있었고
`complete=false`·`naturalWidth=0`·해독 pending·detached=false였다. 원본과 uploads 바이트 대조는 이미 통과했다.
이는 제품의 그림 복사 실패와 구분되는, 화면 밖 lazy 그림을 기다리는 시험 결함이다.

스크롤만 먼저 넣은 후보도 한 번 실패했다. `scrollIntoViewIfNeeded`가 DOM에서 떨어진 요소라고 답했고,
진단에는 새 그림 둘이 연결된 상태로 남았다. `TasksView`는 `/me`의 API 판을 받기 전 `canEdit=false`로
읽기 전용 상세를 그린 뒤, 응답을 받으면 `TaskDetail`이 `ReadOnly`를 `TaskForm`으로 교체한다.
첨부 개수만 기다리면 이 임시 그림을 잡을 수 있다. 최종 편집 폼을 기다린 뒤 그 안의 그림을 잡도록 보완했다.
추가 원인 실험에서는 `/me`를 임시 그림의 해독 시작까지 보류했다가 풀었다. 첫 그림의 해독은 120초 뒤에도
pending이고, 그 그림은 `detached=true`·`connected=false`·`naturalWidth=0`인 반면 새 그림 둘은 DOM에 연결돼 있었다.
즉 단순 지연이 아니라 이미 교체된 옛 그림을 기다리는 실패도 실제로 재현했다. 이 실험에는 긴 메모와 응답 순서 제어가
추가됐으므로 원 CI의 정확한 원인을 증명한 것으로 세지 않는다.

## 수리와 검증

수리는 시험의 관측 대상과 준비 순서에 한정한다. 제품·protocol·권한 코드는 바꾸지 않았다.
기존 파일 바이트·메모·노트·task·brief 링크 단언, 그림 해독 단언과 120초 상한을 유지한다.

- `/me`는 임시 상세가 나타날 때까지 보류한 뒤 사건으로 푼다. 고정 sleep은 없다.
- 최종 `task-form`이 나타난 뒤 그 안의 첨부 둘을 확인한다.
- 각 썸네일을 화면에 넣은 뒤 실제 `img.decode()` 완료를 기다린다.
- 실패 때 마지막 대기 위치·최초 오류·현재 주소·해독 상태·연결 여부·그림 위치를 JSON으로 저장하고 화면도 남긴다.
  최초 오류를 renderer 조회보다 먼저 쓴다. 기존 CI artifact 수집기의 `diagnostics` 경로를 쓴다.
- 긴 메모와 늦은 capabilities 응답은 위 두 결함을 실제 host·agent·브라우저에서 지키기 위해 필요한 회귀 조건이다.
  별도 시험을 늘리거나 기존 시험을 삭제하지 않았다.

| 개발 검사 | 결과 |
| --- | --- |
| 기준 경로 위치 계측·첫 실행 | 통과, 전달 단계 974ms |
| 기준 경로 위치 계측·새 실험실 20회 | 20/20, 전달 단계 912~2452ms |

| 긴 메모·/me를 해독 시작 뒤 전달 | 120초 실패, 교체된 옛 그림 pending·detached=true |
| 긴 메모·기존 해독 순서 | 120초 실패, 화면 밖 그림 pending |
| 긴 메모·스크롤만 추가 | DOM 교체로 실패, 원인 확인 뒤 폼 준비 대기 보완 |

재시도 성공으로 실패를 지우지 않았다. 기준 반복은 간헐성 조사이며, 재현 실패는 각각 다른 코드 후보와
원인 분리 조건으로 남겼다. 반복 실행과 관련 owner는 모두 `aaa verify -- <기존 명령>`으로 실행했다.
개발 중 미커밋 변경이라 workspace finish 원장은 수집되지 않았고 로그는 작업 전용 폴더에 보존했다.
최종 검사는 `aaa verify -- nice -n 15 python3 scripts/verify.py develop --base 039caefd9ecab8128d6985c594ea6cbefbe0a467 --spec 130`이다.
Git 변경은 E130 spec과 Markdown 두 파일뿐이며 웹 전용 범위다. 관련 owner 검사이므로 전체 웹 E2E·전체 Rust·OS cross를
통과했다고 쓰지 않는다. 착지 창의 최종 통합 SHA gate는 이 개발 검사와 별개다.

## CI 회복 여부

원 CI는 첫 실행 실패 상태이며 재실행·회복 증거가 없다.
병합·push·배포와 원 CI 재실행을 하지 않았다. 로컬 통과를 CI 회복으로 쓰지 않는다.
