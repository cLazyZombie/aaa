# 조회 로그인 실패 단계 수리(t-1454)

## 확인한 원인과 한계

실제 로그인에서 공식 CLI가 종료 코드 1로 끝났는데, 기존 완료 처리가 이를 신원 확인/금고 저장 오류로 덮었다.
CLI 실패 때 인증 읽기와 금고 쓰기는 진행하지 않는다. 금고 폴더도 생성되지 않은 상태였다.
메일이 틀렸다거나 금고 저장 권한이 원인이라는 증거는 없다.

기존 코드는 CLI 원문을 폐기하고 고정된 상위 오류만 남겨, 그때 공급자/CLI가 거부한 세부 이유는 복원할 수 없다.
그림의 빈 영역에도 URL이나 오류 내용이 없어 별도 브라우저 원인을 확정하지 않는다.
이번 후보는 잘못된 오류 표시와 진단 유실을 수리한다. 실제 OAuth 실패 자체의 해결이나 5시간 창 복구를 보증하지 않는다.

## 수리 계약

- 공식 CLI의 인증 실패를 그대로 CLI 실패로 표시한다. 인증 읽기·신원 불명/불일치·계정 변경·임시 자료 정리·금고 쓰기는 별도 문구와 고정 단계로 구별한다.
- 종료 전에 모은 제한된 CLI 출력에서 마지막 실패의 고정 분류만 취한다. 지원하는 코드/상태·네트워크·권한·저장·TLS 사유 외에는 unknown이다. 원문·URL·인증 코드·토큰·메일·임의 오류 본문은 로그나 API에 싣지 않는다.
- 실패한 새 로그인은 기존 조회 인증·실행 인증·계정 메타데이터를 바꾸지 않는다. 정상·취소·기기 해제와 소유자 제한은 유지한다.
- 새 API 필드나 요청을 추가하지 않는다. 기존 로그인 error와 host의 비밀 없는 로그를 사용한다. FRONT_API·AGENT_LINK·plan 절·E2E 번호를 늘리지 않는다.

## 개발 검증

관련 owner를 `aaa verify`와 nice 15로 확인했다. 전체 착지 gate·OS cross·production은 별도 승인 뒤 수행한다.

실제 CLI E2E는 종료 코드 1/403의 오류 문구와 정상 조회 금고·실행 인증 보존을 확인했다.
공급자 오류 원문에는 별도 canary를 넣고 응답·로그·상태·프로젝트의 모든 8바이트 조각 비노출을 검사했다.
실제 로그인·재입력·운영 host 변경은 하지 않고 가짜 CLI/인증/키체인/서버만 쓴다.
