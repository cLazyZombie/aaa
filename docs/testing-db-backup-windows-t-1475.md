# Windows 정기 백업 성공 기록 대기 조사(t-1475)

## 현재 결론

원래 CI 실패의 정체 단계는 아직 확정하지 못했다. 기존 시험의 실기 통과를 수리 완료로 보지 않는다.
시한·성공 조건·재시작 뒤 중복 방지 단언을 유지하고, 원인을 구분할 진단을 추가했다.

## 최초 실패에서 확인한 것

기준 `f4145b24`, GitHub Actions run `41543224766`의 Windows job `125612303135`에서
`db_backup::host_ticker_backs_up_once_and_remembers_attempt_after_restart`가 실패했다.

- 실패는 최초 host의 성공 기록 대기다. 재시작이나 재시작 뒤 status 비교까지 가지 않았다.
- predicate는 `status["last_success_ms"].as_u64()`가 값이 있는지 본다.
- host 준비와 `ticker tick` 응답 뒤 `HostWatch::wait_diag`의 5초 안전 상한에 도달했다.
- 마지막 조회는 `last_attempt_ms`가 있고 `last_success_ms`와 `last_error`는 모두 null이었다.
- 이후 CI의 실험실 요약에는 같은 시도의 실제 백업 완료 로그가 있었다. 따라서 완료 전에 host가 죽었거나
  백업이 영구 실패했다고 볼 근거는 없다. 원래 시험은 완료를 관측하기 전에 실패했다.
- 시도에 기록한 기준 시각은 UTC 23:18:17.691, 완료 로그는 23:18:25.050이다. 차이는 약 7.36초다.
  기준 시각은 시도 기록 저장 전에 선택하므로 이 차이는 백업 본체만의 시간이 아니다.
  시도 저장·작업 배정·실제 파일 작업·성공 저장 중 어디가 늦었는지 기존 로그로 나눌 수 없다.
- 기존 실패 진단에 잠금·권한·경로 오류는 없었다. 기록이 없다는 것만으로 각 OS 작업의 지연을 배제하지 않는다.

## 수리 전 실행 대조

같은 코드에 관측 로그만 넣어 Windows 실기에서 실행했다. 고정 sleep·CPU 부하·실패 재시도는 쓰지 않았다.

| 관측 | 결과 |
| --- | --- |
| macOS 백업 유닛 | 7개 통과, 0.63초 |
| macOS 기존 CLI 백업 시험 | 2개 통과, 1.12초 |
| Windows 기존 CLI 백업 시험 | 2개 통과, 0.74초 |
| Windows 단계 계측 | snapshot까지 39ms, 암호화 준비까지 41ms, 암호문 내구 쓰기까지 47ms, 회전까지 48ms |
| Windows `ticker tick` 직후 조회 | 시도 기록 있음, 성공 기록 없음 |
| Windows 실제 완료 로그 뒤 조회 | 성공 시각과 시도 시각 동일, 오류 없음 |

Windows 실기의 빠른 통과는 CI 지연 원인을 설명하거나 원래 실패를 무효화하지 않는다.
실험 프로세스는 직접 만든 자식 handle로 종료하고 종료를 기다렸다. 서비스·예약 작업·사용자 PATH·방화벽은 변경하지 않았다.

## 추가한 진단

`aaa-host::backup`의 debug 로그는 단계명과 누적 경과만 추가한다. 키·경로·오류 원문을 새 필드로 기록하지 않는다.
기존 사용자용 완료·오류 로그는 그대로다. 본체 경과는 validate부터, 비동기·기록 경과는 queue_worker부터 잰다.

- 시도 기록 저장 → worker 배정 → 설정/목적지 확인 → staging/잠금 → 이전 snapshot 정리 → snapshot 복사.
- snapshot 읽기 → 목적지/암호문 생성 → 압축·암호화 → 내구 쓰기 → 공개 → 회전 → 임시 파일과 잠금 정리.
- worker 반환 → 성공 기록 저장 → 오류 초기화 → 완료 알림 전/후.
- 실패 시 I/O 종류·OS 숫자 코드·SQLite 코드. 반환받은 원래 오류 체인에서만 읽는다.

정기 백업 E2E의 두 host에서만 이 debug 로그를 켠다. 시험은 준비·구독·tick 응답·성공 관측·첫 host 회수·
재시작 준비·재시작 tick 응답의 경과를 남긴다. 실패 시 마지막 status에 조회 횟수와 조회에 쓴 시간을 더한다.
진단 때문에 CLI를 추가 실행하지 않으며 성공 predicate, 대기 상한, 재시작 후 status 전체 동일 단언은 바꾸지 않았다.

## 다음 확인

최종 진단 후보를 `aaa verify -- <명령>`으로 확인했다.

| 검사 | macOS | Windows 실기 |
| --- | --- | --- |
| `aaa-host --lib backup::tests::` | 7개 통과 | 6개 통과(Unix 잠금 상속 시험 제외) |
| `aaa --test db_backup` | 2개 통과 | 2개 통과 |
| `aaa --test deps` | 2개 통과 | 2개 통과 |
| `aaa-host --lib` strict Clippy | 통과 | 통과 |
| `aaa --test db_backup` strict Clippy | 통과 | 통과 |
| 실제 성공/없는 경로 실패 관측 | 단계 로그·성공/실패 기록 확인 | 단계 로그·성공/실패 기록 확인 |

없는 경로 실패에서 두 OS 모두 `io_kind=Some(NotFound)`, `os_code=Some(2)`가 남았다.
성공 관측은 `success_recorded`와 동일한 시도/성공 시각을, 실패 관측은 성공 기록 없음과 실제 오류 기록을 확인했다.
보조 관측 도구의 경로·출력 인코딩 오류는 원인을 고쳐 별도 fixture로 확인했으며 CI 지연 재현으로 쓰지 않았다.

이 변경은 원인 수리로 확정한 후보가 아니라 CI 진단 후보다.
별도 착지 승인 뒤 Windows CI에서 정체 단계를 확인하고, 그 근거로 수리한다.
