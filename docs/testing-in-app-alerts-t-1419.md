# 앱 안 알림의 종류와 한 줄 내용 검증(t-1419)

## 바뀐 계약

활동 막대와 앱 안 알림이 질문·보고·작업·아이디어·할 일 등에 같은 아이콘을 쓴다. 토스트는 종류·대상 ID·핵심 내용 한 줄이며 공개 URL을 본문으로 표시하지 않는다. 질문은 실제 질문의 첫 내용 줄, 보고와 완료는 작업 제목, 아이디어는 노트 제목을 쓴다. 긴 글은 48개 글자 묶음까지 줄이고 화면 폭에 맞춰 말줄임한다. 토스트의 접근성 이름도 짧게 유지한다.

알림 목록은 긴 요약과 본문을 「자세히」에서 온전히 연다. 48자보다 짧아도 좁은 화면에서 잘릴 수 있으므로 원문 펼치기는 항상 제공한다. 기존 알림 발생·설정·소리·외부 푸시·대상 화면 이동은 유지하며 Rust·프로토콜·의존성은 바꾸지 않는다.

## 필요한 시험

- `web/test/notificationSummary.test.mjs`: 구조화된 종류·사건에 따른 분류, Markdown 첫 내용 줄, 공개 링크가 핵심 내용을 밀어내지 않음, 여러 코드 포인트로 된 이모지 보존을 검사한다. 서로 다른 종류가 다시 같은 완료 알림으로 보이거나 원문을 잃는 회귀를 막는다.
- E2E 121: 실제 ActivityBar·InboxPanel·Droplet을 렌더한다. Chromium·WebKit의 1280·390px에서 같은 SVG, 한 줄·화면 안 배치·닫기와 비겹침, 원문 펼치기, 짧은 접근성 이름, 실제 누름의 대상 주소 이동을 검사한다. 원문이 48자보다 짧고 본문이 없는 항목도 펼쳐 본다. DOM·실제 애니메이션 완료를 기다리며 고정 sleep을 넣지 않는다.
- E2E 120: 실제 전용 thread가 아이디어를 저장한 사건이 전구 아이콘·「아이디어 갱신」·노트 ID와 제목으로 이어지는지 추가 확인한다. 기존 그림·링크·읽음·푸시·휴대폰 동작 단언을 유지한다.
- 관련 기존 owner: E2E 12의 보고·푸시·읽기, 53의 질문 답변, 114의 알림 500개 끝내기와 저장 ID 보존을 실행했다.

## 확인 중 발견한 시험 문제

첫 화면 시험은 높이가 0인 토스트 바깥 배치 요소의 `visible`을 기다렸다. DOM에는 올바른 종류가 나타났지만 30초 시한으로 실패했다. 실제 보이는 `.droplet-card`를 기다리도록 고쳤다. 시한과 화면 단언은 유지했다.

다음 실행은 전용 시험 문서에 앱의 `herdr/tokens.css`를 불러오지 않아 카드 폭 계산에 쓰는 간격 변수가 없었다. 카드가 1280px로 늘어나 닫기와 겹친다는 단언이 실패했다. 실제 앱의 초기 진입점과 같이 token CSS를 불러오게 고쳤다. 실제 아이디어 사건을 받는 E2E 120은 이 실행에서 통과했다. 단언·시한을 바꾸거나 재시도 옵션을 넣지 않았다.

## 실행 결과

- 웹 타입·번들·웹 유닛 678개와 공개 검사 통과.
- E2E 12·53·114는 최초 관련 실행에서 모두 통과했다. 114의 독립 단계 6개에 알림 500개 끝내기도 포함된다.
- E2E 120은 실제 카드 대기를 고친 뒤 전체 통과했다.
- E2E 121은 token CSS를 앱과 맞춘 뒤 네 조합 모두 통과했다. 새 화면 단계는 각각 약 2.4·2.4·2.7·2.6초였다.
- 개발 검사는 `aaa verify`를 통해 다음처럼 실행한다. Playwright 1.64.1 패키지만 작업 폴더에 두고 기존 공용 브라우저를 사용했다. 전역 설치·브라우저 설치·시스템 설정은 바꾸지 않았다.

```sh
NODE_PATH="$PWD/target/playwright/node_modules" aaa verify -- nice -n 15 \
  python3 scripts/verify.py develop --base origin/main --spec 12,53,114,120,121
```

개발 중 실패와 수리 뒤 통과는 위에 구분했다. 전체 착지 gate는 승인된 착지 창의 최종 통합 SHA에서 실행할 몫으로 남긴다. Windows 전용 변경이 없는 웹 범위다.
